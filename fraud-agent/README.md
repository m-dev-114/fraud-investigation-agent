# AI Fraud Investigation Agent

An end-to-end fintech fraud analyst console: synthetic transaction data with
realistic fraud patterns, a trained ML risk model (XGBoost + Logistic
Regression baseline), and an AI-assisted investigation pipeline that gathers
evidence, explains its reasoning, and hands a recommendation to a human
analyst — never executing a payment decision itself.

> **Live Demo URL:** `https://fraud-investigation-agent-one.vercel.app/`
> **GitHub URL:** `(https://github.com/m-dev-114/fraud-investigation-agen)>`

---

## 1. Overview

```
Transaction -> ML Risk Score -> AI Investigation -> Evidence -> Risk Decision -> Human Review -> Audit
```

1. A transaction comes in (from the seeded synthetic dataset in this demo).
2. An **XGBoost model** scores it for fraud probability.
3. A **LangGraph-orchestrated investigation pipeline** runs six rule + data
   driven sub-agents (transaction, velocity, device, merchant,
   network/location, customer) that each query Postgres for a specific slice
   of context and return weighted evidence.
4. A **deterministic risk-decision engine** blends the ML probability with
   the rule evidence into a single 0–100 risk score, risk level, and
   recommendation (`approve` / `escalate` / `block`).
5. If `LLM_API_KEY` is configured, an LLM writes a plain-English narrative
   summarizing the evidence that was *already* collected. **The LLM never
   sees payment tools and cannot change the score or the recommendation** —
   if it's not configured, or the call fails, a deterministic template
   summary is used instead so the demo always works.
6. A human analyst reviews the evidence, timeline, and fraud network graph,
   then **approves, blocks, or escalates** the case.
7. Every step — tool calls, evidence, model scores, and the final decision —
   is written to an immutable audit log.

## 2. Architecture

```
frontend/  React + TypeScript + Vite + Tailwind + Recharts + React Flow
             │  (Vercel)
             ▼  VITE_API_URL
backend/   FastAPI + SQLAlchemy + LangGraph + scikit-learn/XGBoost
             │  (Render)
             ▼  DATABASE_URL
Supabase   PostgreSQL  (customers, merchants, transactions, devices,
             ip_events, disputes, investigations, investigation_events,
             evidence, cases, model_predictions, analyst_decisions,
             audit_logs)
```

- **Backend** (`backend/`): FastAPI app, SQLAlchemy models for all 13
  tables, ML training/inference, the LangGraph investigation orchestrator,
  and REST endpoints under `/api`.
- **Frontend** (`frontend/`): a Vite + React + TypeScript SPA — Dashboard,
  Transactions, Investigation, Fraud Network (React Flow graph), Audit, and
  Model Performance pages, plus a "Try Demo Investigation" mode.
- **Data & ML**: reproducible synthetic data generator and a training script
  that computes real precision/recall/F1/ROC-AUC/PR-AUC/confusion-matrix
  metrics on a held-out, time-based test split.

## 3. Dataset

Generated by `backend/scripts/generate_data.py` (seed = 42, fully
reproducible):

| Entity | Count |
|---|---|
| Customers | 10,000 |
| Merchants | 1,000 |
| Devices | ~5,100 |
| Transactions | 100,000 |
| IP events | ~96,000 |
| Disputes | ~2,750 |

**Fraud patterns injected** (every transaction has `fraud_label` 0/1 and
`fraud_type`): account takeover, fraud ring, velocity attack, unusual
amount, new device, impossible travel, shared IP/device, and a
failed→successful "card testing" pattern — plus the legitimate baseline.
Overall fraud rate ≈ 6.4%.

Regenerate at any time:

```bash
cd backend
python scripts/generate_data.py      # writes CSVs to data/synthetic/
```

## 4. ML Methodology

`backend/scripts/train_model.py`:

- **Features** (`app/ml/features.py`, shared by training and serving so
  train/serve never drift): amount vs. customer's causal running average,
  time-of-day/weekend, channel one-hots, new-device flag, foreign-transaction
  flag, merchant risk rating, customer risk segment/KYC/account age,
  1-hour trailing velocity (count, sum, failed-txn count), distance from
  home, distance/implied-speed from the previous transaction, and IP/device
  fan-out across distinct customers.
- **Split**: chronological 80/20 (train on the earlier 80% of transactions,
  test on the most recent 20%) — no leakage, mirrors a real production
  rollout.
- **Models**: `LogisticRegression` (baseline, class-balanced) and
  `XGBClassifier` (primary), both with `scale_pos_weight`/`class_weight`
  tuned for the ~6% fraud rate.
- **Metrics are computed, not fabricated.** Example from a real training run
  (yours will vary slightly with the data you generate):

  | Model | Precision | Recall | F1 | ROC-AUC | PR-AUC |
  |---|---|---|---|---|---|
  | XGBoost | 0.990 | 0.978 | 0.984 | 0.999 | 0.996 |
  | Logistic Regression | 0.960 | 0.985 | 0.972 | 0.999 | 0.995 |

  View live metrics (including confusion matrix and feature importance) on
  the **Model** page in the app, served by `GET /api/model/metrics`.

Retrain:

```bash
cd backend
python scripts/generate_data.py   # if you haven't already
python scripts/train_model.py     # writes app/models_store/*.joblib + metrics.json
```

## 5. AI Investigation Workflow

Implemented with **LangGraph** in `backend/app/agents/orchestrator.py` as a
linear, reliable pipeline (deliberately not a complex multi-agent graph —
reliability over cleverness):

`ml_score → transaction_agent → velocity_agent → device_agent → merchant_agent → network_agent → customer_agent → risk_decision → summarize_investigation`

Each node logs `tool_call`/`tool_result` events (visible in the
Investigation timeline and the Audit trail) and returns weighted evidence.
The **risk-decision node is 100% deterministic**: `risk_score = 0.6 × (ML
probability × 100) + 0.4 × (capped rule-evidence weight)`. The LLM layer
(`app/agents/llm_explainer.py`), when `LLM_API_KEY` is set, only narrates
this already-computed evidence — it has no tools and cannot alter the score,
level, or recommendation.

## 7. Environment Variables

**Backend** (`backend/.env`, see `backend/.env.example`):

| Variable | Required | Description |
|---|---|---|
| `DATABASE_URL` | Yes | Supabase Postgres connection string |
| `LLM_API_KEY` | No | Anthropic API key. Omit to use the deterministic engine only |
| `LLM_MODEL` | No | Defaults to `claude-sonnet-4-6` |
| `CORS_ORIGINS` | Yes | Comma-separated allowed origins, e.g. your Vercel URL |
| `ENV` | No | `development` \| `production` |
| `PORT` | No | Set automatically by Render |

**Frontend** (`frontend/.env`, see `frontend/.env.example`):

| Variable | Required | Description |
|---|---|---|
| `VITE_API_URL` | Yes | URL of the deployed FastAPI backend (no trailing slash) |

## 8. Local Setup

**Backend:**

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt

cp .env.example .env
# edit .env: set DATABASE_URL (or leave as sqlite:///./local_dev.db to try locally)

python scripts/generate_data.py     # generate synthetic CSVs (~1-2 min)
python scripts/train_model.py       # train models, compute real metrics (~1 min)
python scripts/seed_database.py     # load CSVs into DATABASE_URL

uvicorn app.main:app --reload --port 8000
# API docs at http://localhost:8000/docs
```

**Frontend:**

```bash
cd frontend
npm install
cp .env.example .env
# edit .env: VITE_API_URL=http://localhost:8000

npm run dev
# App at http://localhost:5173
```

## 9. Supabase Setup

1. Create a project at [supabase.com](https://supabase.com).
2. Go to **Project Settings → Database → Connection string** and copy the
   URI (use the pooled "Transaction" connection string for serverless-style
   connections from Render).
3. Set that as `DATABASE_URL` in `backend/.env` (and later in Render's
   environment variables).
4. Run `python scripts/seed_database.py` **once**, from your machine or any
   environment that can reach Supabase, pointed at that `DATABASE_URL`. This
   creates all 13 tables (idempotent `create_all`) and bulk-loads the
   synthetic CSVs.
5. No manual SQL is required — SQLAlchemy handles schema creation.

## 10. Render Deployment (Backend)

1. Push this repo to GitHub.
2. In Render: **New → Web Service**, connect the repo, root directory
   `backend/`.
3. Build command: `pip install -r requirements.txt`
   Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
   (both are also captured in `backend/render.yaml` if you use a Blueprint).
4. Add environment variables: `DATABASE_URL`, `CORS_ORIGINS` (your Vercel
   URL, added after step 11), optionally `LLM_API_KEY` / `LLM_MODEL`.
5. Deploy. Verify `GET https://<your-render-url>/api/health` returns
   `{"status":"ok", "db_connected": true, "model_loaded": true}`.

`app/models_store/*.joblib` ship in the repo, so no training step is needed
on Render — the API loads them at startup. If you want a fresh model, run
`train_model.py` locally and commit the updated files.

## 11. Vercel Deployment (Frontend)

1. In Vercel: **New Project**, import the repo, root directory `frontend/`.
2. Framework preset: Vite. Build command `npm run build`, output `dist`
   (also captured in `frontend/vercel.json`).
3. Add environment variable `VITE_API_URL` = your Render backend URL.
4. Deploy. Go back to Render and set `CORS_ORIGINS` to this Vercel URL, then
   redeploy the backend so CORS allows it.

## 13. Limitations

- Synthetic data only — no real customer, card, or payment data is used or
  processed anywhere in this project, and it does not integrate with any
  real payment rails.
- The rule-based sub-agents use fixed weights/thresholds tuned against this
  synthetic dataset; in production these would be calibrated against real
  labeled outcomes and reviewed by a risk team.
- The LLM narrative layer is explanatory only — by design it has no tool
  access and cannot take actions or override the deterministic risk engine.
- The free tiers of Render/Supabase/Vercel may cold-start or have
  connection limits; the first request after idling can be slow.
- Feature engineering for velocity/geo signals looks at the whole
  transaction history table per request, which is fine for this dataset
  size but would need materialized/streaming aggregates at real production
  scale.
